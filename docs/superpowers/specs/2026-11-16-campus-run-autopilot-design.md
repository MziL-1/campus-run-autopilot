## 1. 背景与意图

国内多数高校将"校园跑"与体育成绩挂钩，学生需用学校指定的 App 完成跑步打卡。
市场高度碎片化：步道乐跑（600+ 校）、运动世界校园（~500 校区）、闪动校园（300+ 校）
三巨头合计 700+ 高校，其余为云运动、龙猫、自研小程序等长尾。

**本项目的意图**：做一个免费分发的工具，学生输入账号后即可自动完成校园跑打卡，
通过"协议引擎（主力）+ 虚拟定位引擎（兜底）"双引擎覆盖尽可能多的学校平台，
并分阶段交付 Android 与桌面双端。

用户需求的演进轨迹（均已确认）：
1. 登录账号 → 启动程序自动打卡（而非手动跑步）
2. 适配大多数高校，而非单一学校
3. 协议适配与虚拟定位合并进同一个产品
4. 形态选型 → 分阶段双端（先 Android APK，后桌面端覆盖 iOS）
5. 免费分发（非收费代跑业务）

## 2. 目标 / 非目标 / 反目标

### 目标（Goals）

- **G1** Android APK 装上即用：登录 → 一键生成并提交跑步记录 → 可在官方 App 内查到成绩。
- **G2** 协议引擎优先：Phase 1 完成运动世界校园全链路（登录、规则、轨迹合成、OBS 上传、结算、回查）。
- **G3** 虚拟定位引擎作为通用兜底（Phase 1b），覆盖暂无协议适配的平台（步道乐跑、闪动校园等）。
- **G4** 外置配置 + 热更新：协议/规则变化能推送给已分发出去的用户，不依赖用户手动升级 APK。
- **G5** iOS 用户通过 Phase 2 桌面端覆盖（复用协议核心，不碰手机定位）。
- **G6** 免费分发：无支付、无账号系统、无后端数据库。

### 非目标（Non-goals）

- 不做网页面板/服务端代提交（账号密码交给第三方服务器不可接受，云端 IP 易被风控）。
- 不做收费、代跑接单等商业行为（上游许可证禁止，且处于打击面最前线）。
- 不做微信小程序（无模拟定位 API、无法后台定位、过不了审核）。
- Phase 1 不覆盖运动世界以外的协议平台（先深后广）。
- 不做 iOS 原生 App（Phase 2 桌面端覆盖）。

### 反目标（Anti-goals — 出现即视为失败）

- **用户大规模封号**：风控优先级高于功能。宁可少跑、慢跑，不可激进。
- **协议引擎需要 root/ADB 才能用**：协议引擎必须零门槛（装 App → 登录 → 跑）。
- **协议升级后无法远程修复**：没有热更通道 = 产品生命终结。
- **收集用户凭证到开发者服务器**：任何用户数据不得离开用户设备（除必要的目标平台 API 请求）。

## 3. 约束（Constraints）

### C1 市场碎片化
无任何单一平台覆盖"大多数"高校。适配策略 = 协议引擎逐平台击破 + 虚拟定位引擎通用兜底。

### C2 反作弊分层（运动世界为代表）

**客户端层**（协议引擎完全绕过——不运行目标 App 即不触发）：
- 网易易盾 NIS 加固壳（DEX 加密 + SO 保护 + VMP）
- 4 层 GPS 检测（SDK / 系统 / 可信度 / Native 验证）
- 模拟器、root、xposed 检测（学校明文要求卸载此类软件）
- 人脸抽查（商汤 SenseTime + 支付宝人脸 SDK）
- 步频校验（区间 70–240）、SSL Certificate Pinning、DeepKnow 会话证明

**服务端层**（协议引擎必须遵守）：
- 配速窗口（按校配置，如男 3:30–8:30 min/km）
- 必经点 + 2 普通点（无序点位，需经过围栏内指定点）
- 轨迹不得出校园（电子围栏多边形校验）
- 单次距离限值（如男 1–3km/次）、每日计入上限
- 有效时段（如 5:30–20:30）、次数节奏（如 15 次起计分）
- 设备/账号限制：单账号 ≤3 设备、单设备 ≤3 账号，超出判作弊进黑名单
- 提交时间间隔与跑步时长需匹配（防瞬时提交）

**校方处罚**（写入产品风险提示）：
- 查实作弊：清除当次及累计里程、全校通报、额外扣减 40km、累计 3 次本学期 0 分
- 部分学校已引入人脸随机抽检、学期记录大数据回查

### C3 许可证
上游 [Inverx/com.zjwh.android_wh_physicalfitness](https://github.com/Inverx/com.zjwh.android_wh_physicalfitness)
为 **MIT 协议**（含 README 附加声明：严禁商业代跑/倒卖）。
- 本项目免费分发 + 署名致谢 → 可复用上游代码。
- 若未来改为收费 → 必须脱离上游代码独立重写（本设计按免费假设）。

### C4 版本漂移
上游覆盖 App 7.3.40 / 7.3.92；当前客户端已到 7.4.x。
协议实现按 App 版本维护，Phase 1 第一步即为现行版本验证（见 §6）。

### C5 分发与网络环境
- 国内应用商店无法上架（无软著/审核不过）→ APK 直发（网盘/社群/GitHub Releases 镜像）。
- raw.githubusercontent.com 在中国大陆不稳定 → 静态资源需走国内可达 CDN（jsDelivr 等）。

### C6 iOS 平台限制
非越狱 iOS 无法在手机内伪造定位；协议路径不需要定位。
→ iOS 覆盖 = Phase 2 桌面端跑协议提交。

### C7 隐私
凭证仅存用户设备本地（EncryptedSharedPreferences）；不建用户数据库；日志不外发。

## 4. 已定决策（Approaches considered）

### 4.1 产品形态 → 方案三：分阶段双端

| 方案 | 说明 | 取舍 |
|---|---|---|
| 一：纯 Android APK | 双引擎一个包 | 最快，但 iOS 不覆盖 |
| 二：桌面端程序 | 电脑控手机 + 协议 | 全覆盖但每次要开电脑，摩擦大 |
| **三：分阶段双端 ✅** | Phase 1 APK → Phase 2 桌面端复用核心 | 覆盖最全，可分阶段交付 |

排除项：微信小程序（技术不可行）、网页面板（账号/IP 风险）、Xposed 模块（root 门槛过高）。

### 4.2 商业模式 → 免费分发

免费 → 可直接复用 MIT 上游代码、无支付/客服基建、法律风险最低（保留打赏入口不强制）。
收费 → 需独立重写 + 支付交付售后 + 处于代跑产业链打击面，被否。

### 4.3 引擎分工（核心架构决策）

- **协议引擎 = 主力**：不运行目标 App → 客户端检测（GPS 四层、模拟器、步频、人脸）全部落空，
  只需守住服务端规则。体验 = 一键提交，零手机配置门槛。
- **虚拟定位引擎 = 通用兜底**：覆盖无协议适配的平台（步道乐跑/闪动/自研等）。
  注意：对运动世界本身它反而是**最危险**路线（4 层 GPS 检测 + 学校明文禁用虚拟定位），
  产品内需明确提示"运动世界请用协议模式"。

## 5. 系统设计

### 5.1 总体架构

```
┌─ Phase 1: Android APK ──────────────────────────────────┐
│  UI 层：登录 / 一键跑 / 进度查询 / 记录历史 / 设置       │
│                                                          │
│  协议核心（纯 Kotlin/JVM 模块，Android + 桌面共享）      │
│  ├─ crypto    NetSecKit 4.2.4（AES-128-CBC+Feistel KDF  │
│  │            +RSA PKCS#1 v1.5），纯 JVM 实现            │
│  ├─ sign      headerSign/tokenSign + 31 字段 MD5 结算签名│
│  ├─ session   GMT 时钟对齐、token 生命周期管理           │
│  ├─ auth      账号密码登录 + GeeTest v4（见 R2）         │
│  ├─ policy    跑步规则 / 电子围栏 / 必经点 / 人脸抽检区间│
│  ├─ track     轨迹合成（围栏内过点、配速分桶、GPS 噪声） │
│  ├─ upload    OBS 直传 → 结算上报 → 单次记录回查         │
│  └─ telemetry 冷启动/页面曝光埋点模拟（行为一致性）      │
│                                                          │
│  虚拟定位引擎（Phase 1b）：路线模拟 / 速度曲线 / 步频    │
│  更新通道：启动时拉 version.json → 热更配置 / 提示新 APK │
└──────────────────────────────────────────────────────────┘

┌─ Phase 2: 桌面端（Win/Mac）─────────────────────────────┐
│  复用协议核心（Kotlin/JVM）+ GUI/CLI 壳                  │
│  覆盖 iOS 用户（电脑登录提交，不碰手机定位）             │
│  附加价值：定时自动跑（本机调度，无需手机在场）          │
└──────────────────────────────────────────────────────────┘
```

技术选型说明：核心为**纯 Kotlin/JVM 模块**（非 KMP）——两端都是 JVM，
Android 应用直接依赖 JVM 模块即可，比 KMP 构建链简单；未来若需 iOS 原生再评估 KMP。

### 5.2 分期计划

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **1a** | APK 协议引擎（运动世界）+ 更新通道 | 真实账号一键跑，官方 App 内可见有效成绩，通过校方规则校验 |
| **1b** | APK 虚拟定位引擎（通用兜底）+ 定时任务 | 在非运动世界 App 上模拟跑通；运动世界 UI 中标注"不推荐" |
| **2** | 桌面端（Win/Mac）复用协议核心 | iOS 用户经电脑完成提交；支持本机定时任务 |
| 后续 | 步道乐跑 / 闪动 / 云运动协议适配器 | 按需求与可测账号排序逐个击破 |

1b 测试资产已确认（开发者或其朋友持有相关平台账号）→ 1b 直接进入"实现 + 实测"，
仍需先摸清目标平台检测手段，但无需先解决账号问题。

### 5.3 协议核心移植策略

- 上游基准：Inverx 仓库 `协议/7.3.92/` 模块化套件（Python，MIT）。
- 移植到 Kotlin，**保持上游模块边界**（core/login/policy/running/history/…），便于对照与版本 diff。
- 上游"按 App 版本分目录"的维护模式照搬：`protocol/7.3.92/`、`protocol/7.4.x/` 并存。
- 移植而非直接嵌 Python 运行时：APK 体积、Playwright 依赖、启动性能均不可接受。
- **署名义务（MIT）**：App"关于"页与分发说明中保留上游仓库链接与致谢。

### 5.4 关键风险与对策

| # | 风险 | 对策 |
|---|---|---|
| **R1** | 协议版本漂移（7.4.x vs 上游 7.3.92） | 验证路径已定（见 §6.1）：**黑盒为主**——先检索上游是否已有 7.4.x 适配，再用上游 CLI 直连真实服务器逐阶段探测；**仅当需要字段级 diff 时**才自建 PC 端模拟器 + SSL 绕过抓包环境（开发者仅有普通手机，此为 contingency）。更新通道保证失效后可快速推送修复；跟踪上游 Issue 与 App 版本发布 |
| **R2** | GeeTest v4 在 APK 内求解（上游依赖 Playwright+Chromium，不可移植） | 备选方案：(a) 集成官方 GeeTest Android SDK，登录时用户手滑一次（首选，UX 可接受）；(b) WebView 内执行 v4 JS 环境 + 原生图像匹配求解。**Phase 1 spike 定夺** |
| **R3** | 封号（产品生命线） | 见 §5.5 风控设计 |
| **R4** | 上游停更 / 官方施压 | 代码已本地留存，不依赖上游持续存在；收到权利人通知按上游惯例配合下架 |
| **R5** | 分发与更新在国内可达 | 已确认**开源（GitHub 公开仓库）** → jsDelivr 直接可用；APK 分发多镜像（网盘/GitHub Releases）；更新检查拉 `version.json`；下载 URL 可配置多镜像。公开仓库对厂商/学校的可发现性已在决策中接受 |
| **R6** | 人脸随机抽检导致记录异常 | policy 接口可查"人脸抽检区间"；提交前检查，避开抽检窗口；触发时引导用户在官方 App 完成人脸（工具不伪造生物信息） |

### 5.5 风控设计（R3 详则，优先级高于一切功能）

1. **只守服务端规则**：配速落在本校窗口内且自然波动；轨迹在围栏内且经过必经点；
   时长与距离严格匹配；提交节奏符合"跑步中"时间轴（分桶上报，非瞬时提交）。
2. **每用户随机轨迹种子**：同校多用户不得出现雷同轨迹（防关联）。
3. **设备身份与一致性（已定）**：优先上报硬件级标识（如 OAID），使工具与该手机上的
   官方 App 同源（同一物理设备 → 大概率计为同一台）；另生成一个本地持久化的工具侧稳定 ID；
   不尝试读取官方 App 私有存储（无 Root 不可行）。**Phase 1 需验证服务端实际按什么口径
   计设备数**；UI 明示设备占用与"单账号 ≤3 设备"红线。所有设备指纹一经生成本地持久化，
   不频繁变更。
4. **频率自限**：每日次数/公里不超过本校上限；默认比上限更保守（如每日 1 次）。
5. **时段合规**：仅在本校有效时段内提交。
6. **进度可见**：App 内展示本校规则（次数/里程/配速/时段）与当前进度，让用户自己判断。
7. **风险告知**：首启动与设置页明示封号/处分风险，免责自负。

### 5.6 配置系统

- **运动世界**：围栏/点位/配速/时段由 policy API **运行时下发**，本地无需学校配置库；
  仅需平台基础地址与账号体系。学校选择由账号 profile 决定（unid）。
- **未来平台**：按校 JSON 配置（域名、加密参数、跑区数据）随包内置 + 远程热更覆盖。
- 配置 schema 版本化，旧版本 APK 兼容读取。
- **热更边界（已定）**：签名盐、endpoint、字段集、请求头模板等尽量参数化进配置 →
  大多数协议变更走配置热更；**逻辑级变更 = 提示新 APK**，不做脚本引擎/动态代码加载
  （复杂度与安全成本对免费工具不成立）。`version.json` 覆盖：最低 APK 版本、配置版本、
  协议参数版本、下载多镜像 URL。

### 5.7 虚拟定位引擎（Phase 1b）设计要点

- Android 系统模拟位置（开发者选项 → 选择模拟位置应用），**无需 root**。
- 路线：地图选点 / 操场环线预设；速度渐变曲线；GPS 高斯噪声；方向一致（不倒退）。
- 步频模拟：若目标 App 读取加速度/计步传感器，提供对应模拟（传感器 Hook 需评估可行性，
  仅在无 root 前提下做系统级可行方案，做不到则如实标注局限）。
- 目标平台：步道乐跑、闪动校园等无协议适配的 App。
- 对运动世界：UI 显著标注"本平台请使用协议模式，虚拟定位检测风险高"。

### 5.8 Phase 2 桌面端

- Win/Mac，Kotlin/JVM，复用协议核心；UI 可用 Compose Desktop 或轻量 GUI。
- 典型用户：iOS 学生（电脑登录提交）+ 希望定时自动跑的用户（本机调度）。
- 与 APK 共享同一更新通道与配置源。

## 6. 测试与验证计划

1. **协议验证（1a 第一步）**：已确认条件——真实账号可用、学校正在跑期内；逆向资产
   仅有普通手机（无抓包环境）。路径：
   (a) 检索上游仓库 7.4.x 是否已有适配（版本目录 / PR / Issue / 社区分析仓库）；
   (b) 用上游 CLI 直连真实服务器黑盒探测：登录 → 规则拉取 → 轨迹提交 → 官方 App 回查，
       记录各阶段成败，定位与 7.3.92 的差异环节；
   (c) 仅当 (a)(b) 不足以定位时，启用备选任务：自建 PC 端 Android 模拟器 +
       SSL 绕过（JustTrustMePro 类）抓包环境做字段级 diff。
2. **规则符合性**：提交结果必须通过本校规则（配速/点位/围栏/时段），并在官方 App 历史中显示为有效。
3. **灰度顺序**：开发者自用 1–2 周（观察记录稳定性与风控信号）→ 小范围朋友试用 → 公开分发。
   **反馈回路（已定，无后端）**：1a 内置"一键导出诊断包"（脱敏日志、配置版本、最近提交
   结果摘要，输出本地文件），用户手动回传（社群/私聊）。
   **灰度通过标准**：连续 7 天每日提交成功、次日在官方 App 回查均为有效记录、
   无任何风控信号（封禁/记录异常/黑名单提示），方可进入公开分发。
4. **协议回归**：目标 App 每次大版本更新，跑一遍验证清单；失效时走热更通道。
5. **负例测试**：超配速、出围栏、缺必经点的轨迹必须被拦截（验证我们没漏守规则）。

## 8. 留给 Builder 的事项

以下由实现阶段决定，设计层面不锁定：
